# G 1
Q: You just made a commit and realize you forgot to add one file. Nothing is pushed yet. Cleanest fix?
A: git add the file, then git commit --amend
W: git revert HEAD, then commit everything again
W: Make a second commit called "forgot file" and push both
W: git reset --hard HEAD~1, then add the file
E: Amend folds the staged file into the last commit. Fine because nobody else has it yet. (reset --hard would throw away your work.)

Q: git status shows your edited file in red under "Changes not staged for commit." What does that mean?
A: Git sees the change, but it won't be in the next commit until you git add it
W: The file has a syntax error Git detected
W: The change was already committed but not pushed
W: Git blocked the file because it's too large
E: Red = changed but not staged. Green = staged and ready to commit.

Q: A coworker says "pull before you start." You're about to begin work on your laptop. Why?
A: So you build on the latest commits instead of an old copy
W: Pulling uploads your changes so others can see them
W: Git won't let you edit files until you pull
W: Pulling creates a backup branch automatically
E: Starting from a stale copy is the most common cause of surprise conflicts later. Pull downloads; push uploads.

Q: You typed git commit and a strange full-screen editor opened that ignores your typing. What happened?
A: Git opened a text editor (often Vim) for the commit message because you didn't use -m
W: The commit failed and Git is showing an error log
W: Git is waiting for your GitHub password
W: Your terminal froze and needs restarting
E: In Vim, press i to type, then Esc and :wq to save and close. Next time: git commit -m "message".

Q: You edited a file, hated the result, and want it back the way it was at your last commit. Command?
A: git restore <file>
W: git revert <file>
W: git reset --soft <file>
W: git stash drop <file>
E: Discards uncommitted edits to that file. No undo, so be sure. revert works on commits, not files.

Q: You push and GitHub says "Updates were rejected because the remote contains work that you do not have." Safe next step?
A: git pull, resolve any conflicts, then push again
W: git push --force to make GitHub match your copy
W: Delete your local folder and clone again, losing your commit
W: Create a new repository and push there instead
E: Someone (or you on another computer) pushed first. Force-pushing would erase their work.

Q: You accidentally committed .env with your API key. It's NOT pushed yet. Best move?
A: Remove it from the commit, add .env to .gitignore, then amend
W: Push it now and delete the file in the next commit
W: Rename it to env.txt so Git stops seeing it as secret
W: Leave it; a private repo makes it safe
E: git rm --cached .env, add .env to .gitignore, git commit --amend. If it ever reaches GitHub, replace the key.

W: Copy the changed files into a new folder and re-commit there

A: git reset --soft HEAD~1
W: git reset --hard HEAD~1
W: git revert HEAD
W: git checkout HEAD~1
E: Undoing the last commit sits at the top of Stack Overflow's most popular questions of all time. --soft keeps your changes staged.

Q: You added node_modules/ to .gitignore, but Git still shows changes in it. Why?

W: The pattern must be written as *node_modules* to match folders
W: .gitignore only works at the top of main, not on branches
E: Stop tracking it with git rm -r --cached node_modules, then commit.

Q: A merge stops with "CONFLICT (content): Merge conflict in app.js." What do you do?
A: Edit app.js to the correct final code, remove the <<<<<<< ======= >>>>>>> markers, then add and commit
W: Run git merge --continue right away; Git will pick the newest version
W: Delete app.js from both branches and merge again
W: Commit the file with the markers in it and fix it later
E: Git couldn't decide which change wins, so you decide. Then git add app.js and finish the merge.

Q: You want to delete a branch called old-ui both locally and on GitHub. Which commands?
A: git branch -d old-ui and git push origin --delete old-ui
W: git branch -d old-ui (it removes the GitHub copy too)
W: git push origin old-ui --prune
W: git rm -r old-ui
E: Local and remote branches are separate; delete each. Another of Stack Overflow's all-time top Git questions.

Q: git status says "Your branch is ahead of 'origin/main' by 2 commits." Meaning?
A: You have 2 local commits that aren't on GitHub yet
W: GitHub has 2 commits you haven't pulled
W: Your branch has 2 merge conflicts
W: Two of your files have unstaged changes
E: Push to share them. "Behind" would mean GitHub has commits you don't.

Q: You must switch branches for an urgent fix, but you have half-done work you don't want to commit. Best move?
A: git stash, switch and fix, then return and git stash pop
W: git checkout the other branch; your edits stay safely on this branch
W: git reset --hard so the work is saved in the reflog
W: git commit --amend to hide the work inside your last commit
E: Stash shelves changes. Switching with uncommitted edits either fails or carries them to the other branch.

W: They moved to git stash automatically

W: git stash, then switch to main and pop it

W: Their editor re-encrypted the file
W: Git compares files by size, not content
W: They committed from a detached HEAD

Q: You renamed File.js to file.js on a Mac and Git doesn't see the change. Why?

W: Git never tracks renames, only new files
W: The rename only applies after a git pull
W: Git ignores capitalization in .js files
E: Use git mv File.js file.js. Otherwise it breaks later on Linux servers, which are case-sensitive.

Q: Pushing fails with "Permission denied (publickey)." Most likely?

W: You don't have write access because the repo is public
W: Your commit is too large for GitHub
W: Your branch name has a capital letter

Q: You want to see exactly what an AI assistant changed before you commit. Command?
A: git diff
W: git log -1
W: git status -v only
W: git show HEAD
E: git diff shows every added and removed line not yet staged. git show HEAD shows the last commit, not your new edits.

W: Rebase lost your commits; pull first to get them back

Q: Two people edit the same 3,000-line file and hit conflicts daily. Best structural fix?
A: Split it into smaller modules with clear responsibilities
W: Merge less often so conflicts batch up
W: Always choose "theirs" when resolving
W: Have each person work on a long-lived branch
E: Constant conflicts usually point at code doing too many jobs in one place.

Q: Main broke after a merge and production must be fixed in minutes. Most reliable move?
A: Revert the merge commit (git revert -m 1 <hash>) and redeploy, then investigate

W: Reset main to the commit before the merge and force-push
W: Keep the merge and add patches until it works
